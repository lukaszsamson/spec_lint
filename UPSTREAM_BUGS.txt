1. ELIXIR: LOCAL HELPERS DISCARD KNOWN CALL-ARGUMENT INFORMATION

Priority: high for an upstream precision discussion; not a proven bug.
Suggested title: "Local helper indirection loses a literal return shape that
is preserved when the helper is inlined".

Evidence:
  bench/corpus/compiler_counterexamples/helper_insensitivity.ex
  bench/corpus/compiler_counterexamples/check.exs

The sign(:nan) clause passes {:error, :nan} to a private helper that either
raises or returns that argument. The stored return is dynamic(). The otherwise
equivalent sign_inline(:nan) stores {:error, :nan}. Both runtime calls return
the tagged error. This difference determines whether SpecLint can detect the
omission from the declared :negative | :zero | :positive return.

Reproduce without SpecLint:
  elixir bench/corpus/compiler_counterexamples/check.exs

That command was rerun successfully while preparing this document. It compiles
the examples, prints stored checker signatures and verifies runtime witnesses.

Why it matters: the same pattern appears in Decimal.compare/2, Decimal.cmp/2
and Ecto.Changeset.apply_action/2. Ash.UUIDv7.generate/0 illustrates a related
failure to specialize a callee: a known 128-bit generated binary cannot reach
encode/1's :error fallback, but inference retains that alternative.

Ask upstream about preserving argument-to-return relationships or selective
call-site specialization. Do not prescribe unrestricted re-inference of every
callee: recursion, code size and compilation cost need consideration.

Before filing: reproduce the standalone pair on current unmodified upstream;
check for an existing inference roadmap/issue. Present the lost precision,
not the absence of a typespec warning as a compiler contract violation.

2. ELIXIR: HIGHER-ORDER COLLECTION RESULTS LOSE ELEMENT SHAPE

Priority: high for an inference capability request; not a proven bug.
Suggested title: "Preserve mapped result shape through Enum.map/2".

Evidence:
  bench/corpus/compiler_counterexamples/enum_map_result.ex
  bench/corpus/compiler_counterexamples/README.md

On the qualified build:
  Enum.map(atoms, fn atom -> {atom, :tag} end) -> dynamic()
  for atom <- atoms, do: {atom, :tag}         -> dynamic(list({term(), :tag}))

The same check.exs command reproduces this and verifies tags([:a]) == [a: :tag].
The spec [atom()] omits those tuple elements. A comprehension retains more
information, although SpecLint still does not report this particular example:
its list-component counting is a separate limitation, and [] is compatible
with both list types. Improving inference alone is not a measured recall fix.

Related investigations: Enum.reduce/3, Enum.into/2 and Map.new/1, motivated by
Plug.Conn.Query.decode/4, Plug.Conn.merge_private/2 and Ecto association and
preloader queries. Only Enum.map/2 has the standalone paired repro here; do
not claim identical behavior for every operation without separate probes.

Before filing: run on current upstream and ask whether parametric higher-order
signatures are already planned. Keep this separate from helper specialization.

3. ELIXIR/FORK HOOK: UNREACHABLE RETURNS RETAINED UNDER INJECTED DOMAINS

Priority: investigate; NOT ready to report as a stock-compiler bug.
Suggested investigation title: "Spec-domain injection differs from an
equivalent source guard when eliminating unreachable returns".

Evidence:
  test/support/experiment_fixtures.ex: name/1 and display/1
  bench/body_experiment.exs
  bench/corpus/reports/expansion/body_fixtures.json
  bench/corpus/reports/expansion/body_fixture_reproduction.md
  EXPERIMENTS.md: False positives; Upstream bug qualification follow-up

With the patched warnings/7 domain hook, name/1 retains nil from a redundant
clause in the returned signature even though a diagnostic identifies that
clause. display/1 retains the case catch-all's nil under an injected atom()
domain, without the expected unreachable-branch diagnostic. The body experiment
observed this in both the relevant gradual and static-domain checks.

Important negative control: the unpatched qualified compiler correctly warns
and stores only dynamic(:ok) for this ordinary source-level example:

  def display(v) when is_atom(v) do
    case v do
      a when is_atom(a) -> :ok
      _ -> nil
    end
  end

Investigation steps:
  a. Compare the hook's initial variable/context setup with source guards.
  b. Inspect raw local_sigs and the compacted/stored form separately.
  c. Distinguish retained diagnostic metadata from a signature intended for
     downstream type application.
  d. Reduce away SpecLint and the custom hook, if possible.

If it reproduces only under our domain injection, fix or document the hook.
Retaining nil is a precision issue unless it causes a separate demonstrated
incorrect compiler diagnostic or omission of a possible runtime return.

4. ELIXIR: RECURSIVE INFERENCE AND MACHINE-READABLE CHECKER EVIDENCE

Priority: useful follow-up discussions, below the two standalone repros.

Recursion: count([_ | rest]) = 1 + count(rest) is an existing small fixture
whose recursive dynamic() return introduces float() into arithmetic inference.
Investigate bounded fixed-point inference with empty/nonempty, mutually
recursive, nonterminating and raising controls. Do not infer a compiler
arithmetic bug from arithmetic applied to dynamic(). Detailed recursive
qualification and performance measurements remain to be done.

Checker API: request a versioned reader for inferred signatures and explicit
source-clause-to-signature mapping plus redundancy/guard diagnostics. Today
SpecLint re-runs Module.Types.warnings/6 over debug info to avoid gating dead
clauses. That workaround is described in clause_local_qualification.md and
SpecLint.Reachability. Stored clauses can include a pattern whose guard is
impossible even while the compiler correctly warns; consuming those clauses
without the diagnostic was a SpecLint bug, not evidence of compiler unsoundness.

A spec-domain API is a separate feature request (EXPERIMENTS.md, "Minimal
compiler API"). It should specify fresh target contexts, return representation,
cost and unknown reachability explicitly. "No redundancy warning" must not
be advertised as proof that a clause executes. An API alone will not repair
lost helper, collection or recursive return precision.

7. ELIXIR: Descr.list_tl/1 EXCLUDES AN ACHIEVABLE TAIL (reproduced, algebra)

Priority: report. It is a soundness bug in a projection, independent of any
SpecLint code. Suggested title: "list_tl over-excludes: tail of
list(atom()) minus list(:y) drops [:y]".

Repro (current tree):
  import Module.Types.Descr
  t = opt_difference(list(atom()), list(atom([:y])))
  {:ok, tl} = list_tl(t)
  to_quoted_string(t)   #=> "non_empty_list(atom()) and not non_empty_list(:y)"
  to_quoted_string(tl)  #=> "list(atom()) and not non_empty_list(:y)"
  subtype?(non_empty_list(atom([:y])), tl)   #=> false
  disjoint?(non_empty_list(atom([:y])), tl)  #=> true

Why it is wrong: [:x, :y] belongs to t (it is a non-empty list of atoms and
is not a list made only of :y). Its tail is [:y], which belongs to
non_empty_list(:y). The projection claims that tail is impossible
(disjoint), so list_tl under-approximates. The correct result is
list(atom()) with no exclusion: once the head has been removed, nothing is
known about whether the remaining elements are all :y.

Likely cause: list_tl keeps the negative literal of the difference
(`not non_empty_list(:y)`) on the tail, but a negated "all elements are :y"
constraint on the whole list does not transfer to its tail.

Impact today: low in practice. The checker does not currently produce
`list(A) and not list(B)` types from patterns (it does not refine a
variable by the negation of earlier clauses), so I could not trigger a false
warning from source. It will matter as soon as negative list refinements
reach hd/tl typing. This is the same finding the verification branch
recorded as "List-tail projection" in VERIFICATION_RESULTS.md; the branch's
finite model rejected it, and the direct probe above confirms it on the
current tree without the model.

Before filing: add the four-line probe as a failing test in
lib/elixir/test/elixir/module/types/descr_test.exs, and check whether
list_hd has the dual problem (it did not in a quick look, but I did not
probe it).

8. ELIXIR: PRINTER MERGES fun(n) WITH (none(), ... -> term()) (reproduced)

  to_quoted_string(fun(2))                       #=> "(none(), none() -> term())"
  to_quoted_string(fun([none(), none()], term())) #=> "(none(), none() -> term())"
  equal?(fun(2), fun([none(), none()], term()))   #=> false

Two unequal types print identically. Any tool (and any human) reading
diagnostics cannot tell "some 2-ary function" from the bottom-argument
arrow. The verification branch recorded this as printer finding I1.
Suggested fix: print fun(n) as `(... -> term())` with an arity marker, or as
`fun(2)`, and reserve the arrow form for actual argument types. Low
priority, but cheap, and it removes a class of misleading messages.

9. ELIXIR: A MAP EQUAL TO map() PRINTS AS AN 11-DOMAIN LITERAL (reproduced)

  doms = for k <- [:atom, :integer, :float, :binary, :bitstring_no_binary,
                   :pid, :port, :reference, :tuple, :map, :list, :fun],
         do: {[k], term()}
  m = closed_map(doms)
  equal?(m, open_map())  #=> true
  to_quoted_string(m)    #=> "%{atom() => term(), bitstring() => term(),
                              float() => term(), fun() => term(), ...}"

Such maps arise from every spec written as %{optional(any()) => any()} or
from Calendar.datetime()-style types once translated. The printer should
normalise a closed map whose domains cover every key kind with term()
values and no required keys to `map()`, and more generally collapse
domain-complete maps before printing. Presentation only; no unsound result
observed. (SpecLint works around it in its own canonical printer.)

11. ELIXIR (UPSTREAM 648b2a9): for ... into: NARROWS THE BODY TO bitstring()
    WHEN THE COLLECTABLE MAY ALSO BE A LIST (reproduced, unsound signature)

Compiler: upstream 648b2a94934664cfd2c788348d02d799c68faa69 (unmodified,
built with bench/corpus/toolchain/build_elixir.sh), OTP 28.5.0.1.
Suggested title: "for-comprehension with a bitstring-or-list :into narrows
the body variables to bitstring()".

    defmodule IntoProbe do
      @spec f(boolean(), atom()) :: atom()
      def f(flag, value) do
        into = if flag, do: [], else: ""
        _ = for _ <- [1], do: value, into: into
        value
      end
    end

Stored signature (ExCk) on 648b2a9:
    (term(), bitstring()) -> dynamic(bitstring())
On c24c235 (fork fix): (term(), term()) -> dynamic()
Runtime: IntoProbe.f(true, :ok) returns :ok on both.

The stored domain excludes :ok, which the function accepts: unsound, not a
precision loss. A caller passing an atom gets a false type warning, and
SpecLint reports a gating SL003 (spec_domain_rejected) on the correct spec
above (exit 1 in CI). The same code path warns on the literal form
`for _ <- [1], do: :ok, into: into` ("expected the body of a
for-comprehension with into: binary() ... to be a binary"), also a false
positive: the list path accepts any element. Cause: for_into/5 in
lib/elixir/lib/module/types/expr.ex returns bitstring() as the body's
expected type when the collectable may be a bitstring, even when it may also
be an empty list; the fork commit "Fix incorrect narrowing in mixed type for
into" returns term() for that case and only reports badbitbody when the list
path is impossible. Regression test:
test/spec_lint/upstream_qualification_test.exs (pinned per revision).
Not observed in the fifteen corpora (no stored signature of their own
applications differs between the two compilers except semantically equal
terms).

12. LIBRARY (phoenix_view): INJECTED template_not_found/2 SPEC IS no_return

Priority: candidate library-spec report; NOT a compiler bug. Not filed.
Found: Milestone 7 adoption trials (2026-09-30), anonymised as
test/support/adoption_fixtures.ex (Library/Consumer) and asserted by
test/spec_lint/adoption_regressions_test.exs.

Phoenix.View's __using__/1 injects
  @spec template_not_found(binary, map) :: no_return
together with a raising default definition and defoverridable. Applications
routinely override template_not_found/2 to return a rendered binary (the
generated ErrorView does). The injected spec stays attached to the override,
so the override's inferred return (binary) contradicts the declared
no_return: SpecLint reports SL006 unexpected_return, correctly, but the spec
is owned by the library, not the application. SpecLint presents a possible-inheritance note (bare-line spec annotation),
which is heuristic and does not establish library ownership by itself.

Before filing: check current phoenix_view (and Phoenix 1.7+ component-based
error rendering, which may no longer use it), search for duplicates, and
propose either no spec on the overridable default or a return type that
admits the documented override (for example String.t() | no_return, or
term()).

M8 verification (2026-09-30): the declaration remains in upstream main at
87159b55dea9f68147943f46a2996727b7d20268, lib/phoenix_view.ex.
https://github.com/phoenixframework/phoenix_view/blob/87159b55dea9f68147943f46a2996727b7d20268/lib/phoenix_view.ex
Prior related work exists and must be considered before filing:
https://github.com/phoenixframework/phoenix_view/pull/7 (merged removal of
an overridable spec in the then lib/phoenix/template.ex; linked Elixir
issue 11574), and https://github.com/phoenixframework/phoenix_view/issues/8
(closed Dialyzer no-local-return discussion after 1.1.1). This is not a
newly discovered problem family. No issue or comment was submitted.
Do not assume binary() is the complete callback contract: views also
return structured JSON data. Any proposed replacement type must account
for the documented rendering contract; removing the inherited spec is
an alternative to discuss with maintainers.
